# Windows Batch Scripting (git-bash host)

Правка, отладка и «хирургия» .bat/.cmd-скриптов на Windows-хосте, где terminal работает через git-bash (MSYS). Проверено при выпиливании целой подсистемы (kobold/GPU) из проекта Hermes-Portable-Scripts.

## CRLF — ОБЯЗАТЕЛЬНО для Windows-установки (выделено по требованию пользователя!)

.bat обязан быть CRLF (подробности — п.5 ниже). **Установщики репозитория ДОЛЖНЫ сами
нормализовать CRLF после git pull / write_file / sed** (иначе cmd ломается:
«'VERSION' is not recognized», goto-метки плывут, строки склеиваются).
Готовый инструмент: `scripts/py/normalize_crlf.py` (идемпотентен; `--check` — проверка):
- вызов из .bat-установщика: `"%PY%" "%SCRIPTS_DIR%\py\normalize_crlf.py" "%ROOT_DIR%"`
  (ROOT_DIR — ПЕРВЫЙ аргумент; `--check` — вторым: `normalize_crlf.py <ROOT> --check`)
- верификация прогона: вывод «CRLF: обработано N .bat — исправлено M»; M>0 — были LF
- verify_batch.py (scripts/ в этом скилле) теперь включает check_crlf (orphan-LF == 0)

## Скачал дистрибутив вручную — СРАЗУ черкай скрипт установки (правило пользователя!)

Если агент качает бинарник/архив вручную (llama.cpp, cudart, модели, Electron) —
ОБЯЗАТЕЛЬНО сразу же создать/обновить установочный скрипт (InstallOrUpdate-*.bat /
install_*.ps1) в репозитории: загрузка через скрипт должна быть воспроизводимой
(URL + распаковка + финальная проверка). Вручную качать и НЕ фиксировать скрипт —
нарушение (пользователь: «когда качаешь дистрибутив — сразу черкай скрипт установки!»).

## for /f + вызов python/внешней команды — ДВОЙНЫЕ кавычки (cmd /c паттерн, 2026-08)

`for /f ... in ('"%PY%" "C:\путь\скрипт.py"')` — cmd падает: «The filename, directory
name, or volume label syntax is incorrect» (exit 1, пустой вывод). Для for /f нужен
ДВОЙНОЙ уровень кавычек (cmd /c паттерн):

```bat
REM ПРАВИЛЬНО (открывающая "" и закрывающая "" — cmd /c паттерн):
for /f "delims=" %%a in ('""%PY%" "%SCRIPTS_DIR%\py\script.py""') do set "VAR=%%a"
REM НЕПРАВИЛЬНО (одинарный уровень — cmd путается):
for /f "delims=" %%a in ('"%PY%" "%SCRIPTS_DIR%\py\script.py"') do set "VAR=%%a"
```

Эталон в репо: строка PICK в InstallOrUpdate-Llama.bat (двойные кавычки работают;
реальный прогон через временный bat с той же строкой — проверка перед коммитом).

31s. **Загрузка дистрибутивов — грабли (13.08.2026, llama.cpp/Electron!).** (1) Имена ассетов GitHub — НЕ хардкодить: llama.cpp переименовал `llama-bin-win-*.zip` → `llama-<build>-bin-win-*.zip` — старый URL = 404. Имя брать через GitHub API `releases/latest` (python-скрипт `llama_latest_asset.py` — `json.load(urllib.request.urlopen(...))` — фильтр по `cuda-13.3` + `x64`). (2) Прокси-фоллбэк — по правилу пользователя: `curl -L --noproxy "*"` (прямой) → `if errorlevel 1` → `curl -L -x http://127.0.0.1:10809` (прокси — ТОЛЬКО для этой загрузки; НЕ глобальный env — всё через прокси медленно!). (3) for /f вызов python из .bat: ДВОЙНЫЕ кавычки — `for /f "delims=" %%a in ('""%PY%" "%SCRIPTS_DIR%\py\x.py""') do set "VAR=%%a"` — одинарные (`'"%PY%" ...'`) дают «The filename... syntax is incorrect» (cmd /c не может разобрать). Паттерн — как рабочий `PICK` (строка 100 InstallOrUpdate-Llama.bat). (4) ПРАВИЛО ПОЛЬЗОВАТЕЛЯ: загрузки — в %TEMP%-каталог → там разворачивать → ПРИ УСПЕХЕ move в целевой → очищать ошмётки (temp + архивы); не мусорить в целевом незавершёнными загрузками! (5) set+use переменной в одном if/for-блоке: `!VAR!` (delayed) — `%VAR%` расширяется при парсинге блока (всегда пусто → ложный [ERROR]!). (6) unzip в cmd НЕТ (только MSYS!) — `tar -xf` (bsdtar — встроен в Win10+). (7) Архивы с вложенной папкой: сдвигать содержимое в корень (for /d + move) перед проверкой exe. ВНИМАНИЕ: скиллы в data\hermes\skills перезаписываются xcopy из scripts\skills при каждом [3] — патчить НУЖНО репо-версию (scripts\skills\...), потом синхронизировать на машины!

## Когда использовать

- Правка/чистка .bat-скриптов (меню, установщики, запускатели)

- Выпиливание функциональности из скриптового проекта

## Критические pitfall'ы (все проверены на практике)

1. **git.exe и python.exe — Windows-бинарники, НЕ понимают MSYS-пути** (`/d/Hermes`, `/c/foo`):
   - `git -C /d/Hermes status` → `fatal: cannot change to '/d/Hermes'`
   - `cd /d/Hermes && python /c/path/script.py` → интерпретируется как `D:\c\path\...` → `can't open file`
   - Решение: передавать Windows-пути (`git -C "D:/Hermes"`, `python "C:/path/script.py"`). MSYS-утилиты (ls, grep, sed) пути понимают.

2. **Кодировки bat с кириллицей**:
   - `chcp 65001` в начале + файл в UTF-8 — работает, но капризно.
   - Надёжно для русской Windows: файл в **CP866** + `chcp 866` (или без chcp — OEM по умолчанию 866).
   - write_file пишет UTF-8 → конвертировать: `iconv -f UTF-8 -t CP866 file > tmp && mv tmp file` (iconv есть в git-bash).
   - .ps1 держать чистым ASCII — тогда кодировка не важна (PS 5.1 читает UTF-8 без BOM как ANSI).

3. **`git rm` падает целиком, если один путь не найден**: `fatal: pathspec 'X' did not match`. Файл может быть в `.gitignore` (например, локальный `Config.ini`) — тогда он в git не отслеживается, удаляй обычным `rm`, а не `git rm`. Проверяй `.gitignore` перед `git rm`.

4. **subprocess.run(["grep", ...]) из python на Windows** — падает (grep не в PATH Windows-процесса). Внутри python используй os.walk/re, а grep — только в terminal (git-bash).

5. **.bat обязан быть CRLF, а не LF (жёсткий урок 2026-08).** `write_file` пишет LF; cmd на LF-only .bat ломается: goto-метки «плывут», строки склеиваются, и пачкой летят `'...' is not recognized as an internal or external command` от обрывков слов. Симптом: скрипт «почти работает», но мешает текст. Конвертация новых файлов после write_file (обязательно!):
   `python -c` заменой `data.replace(b"\r\n", b"\n").replace(b"\n", b"\r\n")` (или unix2dos). Проверка: `(data.count(b"\n") - data.count(b"\r\n")) == 0`. Патчи (patch-инструмент) в уже-CRLF-файлах CRLF сохраняют — конвертировать нужно только новые write_file-файлы. **Правка СУЩЕСТВУЮЩЕГО CRLF-файла через python/heredoc (2026-08): СНАЧАЛА нормализуй `data = data.replace("\r\n", "\n")`, потом правь, потом `data.replace("\n", "\r\n")` обратно** — иначе вставленный блок с `\n` соседствует с исходными `\r\n`, файл получает смесь переводов строк, а проверка `count(b"\n") - count(b"\r\n") == 0` честно падает.

6. **Незаэкранированные скобки `()` в echo/set /p ВНУТРИ if-блока — «... was unexpected at this time».**
   cmd не понимает вложенные скобки: первая `)` в тексте echo-строки ЗАКРЫВАЕТ if-блок преждевременно, дальше — каша и ошибки. Пример: `echo Запустите (ПКМ -^> ...)` внутри `if !errorlevel! neq 0 ( ... )`. Экранировать ВСЕ текстовые скобки в строках внутри блоков: `^(` и `^)`. Это же нашлось в готовом InstallOrUpdate-RU.bat (строка `echo ... (terminal.cwd)...` в if-блоке — скрипт молча не доходил до patch_terminal_cwd). Верификацию дополнить: для каждой echo/set /p строки без `^(`/`^)` внутри блоков — флаг. Реальный случай 2026-08: `echo ... Desktop-зависимости (Electron) — пропущено ^(web-режим сервера^)` — первая `)` после `(Electron` разрывала if-блок → «was unexpected at this time» сразу после блока; фикс — `^(Electron^)` (грепать `^(«(Electron)» без `^(` в echo внутри блоков).

7. **`set /p` с pipe-вводом: читается ТОЛЬКО ПЕРВЫЙ (жёсткий урок 2026-08).** При перенаправленном stdin (subprocess input) cmd читает вход блоками (read-ahead): первый `set /p` забирает всё, ВСЕ последующие `set /p` в том же батнике возвращают ПУСТО — даже с ЯВНЫМИ значениями в input (`A=[AAA] B=[]` для двух set /p подряд БЕЗ call; в Install-Hermes-Service имя прочиталось, а порт/логин/пароль — пусто, отсюда «пароль никогда не доходит»). Пустые Enter'ы дефолты тоже не дают. `call` ЛЮБОГО дочернего .bat (даже пустого) съедает остаток pipe; `call x.bat <nul` НЕ спасает (и сам может убить stdin родителя навсегда). **РЕШЕНИЕ для автоматизации: не гонять много set /p — принимать значения параметрами командной строки (`%~1`..`%~4`), set /p оставить интерактивным fallback** (`if not defined SERVICE_NAME set /p ...`). Интерактивно (консоль) set /p работает нормально — ломается только pipe. (Побочно: heredoc-прогоны с input триггерят approval — предупреждать пользователя или дать запустить ему самому.)

8. **Дочерний .bat через `call` ЗАТИРАЕТ переменные родителя (2026-08, REQUESTED_NAME).** Хелпер, возвращающий результат через `endlocal & set "SERVICE_NAME=%FOUND%"`, перезаписывает SERVICE_NAME в вызывающем скрипте — даже если тот только что ввёл своё значение через `set /p` (пустой FOUND → имя обнулено → «CreateService: имя службы не может быть пустым»). Паттерн: до вызова хелпера сделать снапшот (`set "REQUESTED_NAME=!SERVICE_NAME!"`), вызвать, прочитать результат в ДРУГУЮ переменную, восстановить.

9. **Диагностика set /p: `%VAR%` в ТОЙ ЖЕ строке после `&` не видит set /p** (раскрытие при парсинге строки — до выполнения). `cmd /c "set /p X=... & echo GOT=[%X%]"` всегда покажет пусто — это НЕ значит, что set /p сломан. Корректная проверка: `cmd /v:on /c "set /p X=... & echo GOT=[!X!]"` (delayed expansion) или отдельная строка. Минимальный воспроизводящий тест на set /p: `@echo off` + setlocal + ESC-переменная через `for /f "delims=#" ... 'prompt #$E# & echo on & for %%_ in (1) do rem'` + set /p + `echo RESULT=[!VAR!]` — если работает, виновника ищи ДО set /p (другой set /p в невыполнившейся if-ветке съедает строку из pipe, дочерний call затирает переменную, скрипт-копия в другом каталоге сломала пути `%~dp0..`).

10. **Локализованный вывод `sc` на RU Windows.** `sc query` / `sc qdescription` печатают ключи ПО-РУССКИ: `ИМЯ_СЛУЖБЫ:`, `ОПИСАНИЕ_СЛУЖБЫ:`, `СОСТОЯНИЕ:` — findstr по английским `SERVICE_NAME`/`SERVICE_DESCRIPTION`/`STATE` молча не находит (значения `RUNNING`/`STOPPED` остаются английскими — по ним грепать можно). Ищи по СОДЕРЖИМОМУ (путь инстанса), не по ключу. Парсинг имени из `sc query`: `tokens=1* delims=:` (НЕ `tokens=2` — путь `D:\...` содержит `:` и обрежется!), ведущий пробел срезать `set "SN=!SN:~1!"`, НИКОГДА не `!SN: =!` (убьёт пробелы ВНУТРИ имени службы типа `HermesGateway (D_Hermes)`).

11. **findstr без входного потока читает STDIN.** Внутри `for /f ... in ('команда ^| findstr ...')` — если источник pipe ничего не вывел (команда упала с `2>nul`), findstr начинает читать родительский stdin и съедает ввод, предназначенный следующим `set /p`. Лечится тем же правилом, что и п.7: автоматизация через параметры, а не через pipe-ввод.

12. **Экранирование путей при «хирургии» .bat (2026-08).** (а) patch-инструмент парсит new_string как JSON: `\release` в пути превращается в CR + `elease` (байтовое искажение — «desktopelease», «win-unpackedesources»); (б) heredoc `\\a` может стать BEL `\x07`. После многошаговой правки путей ОБЯЗАТЕЛЬНА байт-верификация: `count(b"\n") - count(b"\r\n") == 0` (LF-only = сломан), `count(b"\x07") == 0` (BEL), grep «elease»/«esources» без «release»/«resources». Надёжный способ правки: фиксер через write_file (НЕ heredoc) с raw-строками `r'...'`, замена ЦЕЛОГО блока по маркерам (`i1 = text.find(start_marker)`, `i2 = text.find(end_marker)`, склейка `text[:j] + new_block + text[i2:]`, j = последний `REM ====` перед start_marker), а не точечные byte-замены. Осторожно: якоря i1/i2 берут ПЕРВОЕ вхождение — если патч ранее дублировал секцию, фиксер вырежет ВСЁ между якорями (так был потерян nssm-блок между web_dist и Firewall; восстановление — вставкой блока по маркеру «REM   web_dist»).

   12b. **`text.find(":label")` ловит `goto :label`, а не метку (2026-08, fallback-блок Deps).** При вырезании блока до метки `find(":warn_continue")` нашёл строку `if not defined warn_choice goto :warn_continue` (первое вхождение подстроки — goto тоже содержит `:label`!) → хвост блока (set warn_choice / if 0 → VPN-выход) остался после вставки, а в файле завелись ДВЕ метки `:warn_continue`. Надёжно: искать метку СТРОГО на своей строке — `find("\n:label\n")` (после нормализации `\r\n`→`\n`), либо удалять диапазон `[первая_метка : вторая_метка]` целиком. После вырезания проверять: `count(":label")` — сколько осталось, и grep `goto :label` — если goto не осталось, метка вообще не нужна (можно убрать обе).

   12c. **Не-raw python-строки в heredoc-вставках: `\u`/`\N`-эскейпы падают на путях (2026-08).** Вставляя в .bat блок с путями через heredoc-python: `"%HERMES_HOME%\\ui-tui\\node_modules"` в ОБЫЧНОЙ строке → python видит `\u` → `SyntaxError: (unicode error) 'unicodeescape' codec can't decode bytes ... truncated \uXXXX escape` (и `\r` в `\rg.exe` молча превращается в CR — не падает, но ломает сравнения). Решение: вставляемые блоки с бэкслешами — ТОЛЬКО raw-строки `r"""..."""`. Тот же принцип в ВЕРИФИКАТОРАХ: паттерн проверки `"bin\\rg.exe" in text` — это `bin` + CR + `g.exe`, никогда не совпадёт с текстом файла `bin\rg.exe` — использовать `r"bin\rg.exe"` (raw!).

   12d. **Raw-строка в heredoc-верификаторе ломается при записи в tmp-файл (2026-08, три ложных FAIL подряд).** Паттерн `r'...\bin\...'` внутри `r"""..."""`-heredoc сохраняется буквально при записи в tmp-файл, НО при ВЫПОЛНЕНИИ tmp-файла python'ом строка уже НЕ raw: `'\bin\'` → `\b` = backspace (0x08), `\f` = formfeed — проверка `'...\bin\ffmpeg.exe...' in text` ложно FAIL'ит при правильном файле. Лечение: в паттернах верификаторов ИЗБЕГАТЬ бэкслешей (`'ffmpeg.exe" set "WEBTOOLS_OK=1"'` вместо полного пути), либо писать ДВОЙНЫЕ (`'\\bin\\'` → при выполнении станет `\bin\`). Точность паттернов: `"-version" not in file` ложно цепляет `git --version` — проверять `'ffmpeg.exe" -version' not in file`.

13. **findstr: паттерн с ведущим «-» = опции; угловые скобки в echo = перенаправление; ведущий пробел из ipconfig (все из Connect-Guide.bat, 2026-08).**
   - `findstr /i /r "--port [0-9]*"` → `FINDSTR: /- ignored ... Bad command line` (findstr разбирает `--port` как набор опций и падает). Лечение: литерал через `/c:` — `findstr /c:"--port"` (всё после `/c:` — строка, не опции; `/r` с `/c:` не нужен). Дальше `tokens=2` забирает номер порта.
   - `echo http://<IP-сервера>:9119` → cmd видит `<` как перенаправление ввода: «The system cannot find the file specified» (пытается читать файл «IP-сервера»). Экранировать ОБЕ скобки: `echo http://^<IP-сервера^>:!SERVICE_PORT!`.
   - `for /f "tokens=2 delims=:" %%i in ('ipconfig ^| findstr /i "IPv4"')` даёт IP с ВЕДУЩИМ пробелом (после двоеточия) → `http:// 192.168.0.30` (двойной пробел). Чистить: `set "CURIP=%%i"` + `if defined CURIP set "CURIP=!CURIP: =!"` (для IP удаление всех пробелов безопасно; для имён служб НЕЛЬЗЯ — см. п.10).
   - Живая проверка гайда после правок: прогнать `cmd /c <script>` со stdin-Enter и grep-нуть вывод на «FINDSTR», «cannot find», двойной пробел после http://, «0.0.0.0», порт.

   13b. **Пробел в `for /f delims=` — ТОЛЬКО в КОНЦЕ списка (2026-08, InstallOrUpdate-Plugins.bat «версия не парсится»).** `delims=: ,` (пробел МЕЖДУ символами) ломает for: пробел в строке опций — РАЗДЕЛИТЕЛЬ опций, `,` становится отдельной опцией → `," was unexpected at this time`. Правильно: `delims=:, ` (пробел ПОСЛЕ запятой, в самом конце списка). Без пробела в delims ведущие пробелы строки (JSON `  "version": ...`) остаются ВНУТРИ первого токена → сравнение `"%%a"=="..."` молча не матчится. Симптом «версor не парсится / статус всегда "?" при работающем for» — первым делом проверить пробел в delims.

   13c. **`\"` в cmd — НЕ escape: бэкслеш ЛИТЕРАЛЕН (2026-08, сравнение `"%%a"=="\"version\""`).** В .bat нельзя «экранировать» кавычку бэкслешем: `\"version\"` — это `\` + `"version"` + `\`, сравнение `""version""` == `"\"version\""` всегда FALSE. НО `findstr /c:"\"version\""` в for /f КОРРЕКТНО находит строку `"version": "2.0.14",` (cmd снимает внешние кавычки аргумента — паттерн реально `"version"`). Рабочий паттерн «вытащить версию из package.json в .bat» (замена хрупкому перебору tokens по всему JSON):
```bat
for /f "usebackq tokens=2 delims=:, " %%v in (`findstr /c:"\"version\"" "%HERMES_HOME%\memos-plugin\package.json"`) do (
    set "MEMOS_VERSION=%%v"
    set "MEMOS_VERSION=!MEMOS_VERSION:"=!"
)
```
`!VAR:"=!` (delayed-замена кавычек на пусто) внутри `set "..."` — работает. Пробел в конце delims обязателен (13b): token1=`"version"`, token2=`"2.0.14"` (ведущий пробел строки режется delims-пробелом). Сравнение с литералом, содержащим кавычки, в cmd вообще не делать — выносить в findstr или в python.

15. **Delayed expansion ломается на «!» в тексте echo-строк (2026-08, «SERVICE_PORT»).** cmd с `enabledelayedexpansion` парит восклицательные знаки ПОПАРНО: `echo   ! Порт !SERVICE_PORT! НЕ слушается на 0.0.0.0!` (ТРИ `!` — текст + переменная) → первая `!` открывает, вторая закрывает → переменная « Порт » (не существует → пусто), `SERVICE_PORT` остаётся ЛИТЕРАЛОМ, третья `!` съедает хвост до конца строки. Итог вместо текста: `    SERVICE_PORT`. Симптом-маркер: в выводе виден ГОЛЫЙ идентификатор переменной без `!` и без окружающего текста. То же: `[!] Пароль ... 0.0.0.0!` выводится как `[`. **Правило: в echo-строках с `!VAR!` НЕ использовать текстовые `!` вообще** (заменять на «ВНИМАНИЕ:», «[WARN]», точку) — одна пара `!VAR!` работает, две пары тоже, а вот текстовая `!` + переменная = поломка. Эмпирическая проверка: `grep -n "echo.*!" file.bat | awk -F: '{n=gsub(/!/,"!",$0); if (n>1) print}'` — просмотреть все echo-строки с 2+ `!` и убедиться, что они парные (только `!VAR!`). Изолированный тест: bat с `set "SERVICE_PORT=9123"` + `if`/`else` с этими echo — при неслушающемся порте вывод должен содержать полный текст с раскрытой переменной.

16. **Вложенные кавычки в `for /f '...'` и `cmd /C` ЛОМАЮТ команду (2026-08, хэш пароля).** `for /f "delims=" %%h in ('"%PYTHON_EXE%" -c "from ... import hash_password; print(hash_password('!AUTH_PASS!'))"')` — cmd НЕ различает `'` и `"`: кавычки парятся попарно, `print(hash_password('` ломает команду → python падает, `2>nul` скрывает → переменная пуста, «Не удалось сгенерировать хэш пароля». `python -c "...sys.argv[1]..."    16b. **`for /f "usebackq"` с backtick: кавычки ВНУТРИ команды молча ломают выполнение (2026-08, Connection.bat «Логин: не задан»).** `for /f "usebackq delims=" %%u in (`"%PY%" -c "print(42)"`)` — вывод НЕ захватывается: переменная пуста, stderr пуст, exit 0 (в отличие от п.16 — там явный crash). `"%PY%" -V` (без внутренних кавычек) работает. Максимум — упомянуть находку одной строкой в отчёте. Сначала зафиксировать и откатить собственную несанкционированную правку (`git checkout -- <file>`).

   31d. **Перед пушем — `git fetch`, мог закоммитить сам пользователь (2026-08).** Пока агент правил на полигоне, пользователь закоммитил фикс на ДОМЕ (`324f0dc`) и запушил в origin — push полигона отклонён (non-fast-forward), свой коммит пришлось отменять (`git reset --hard origin/main`) и накладывать только реальный дельтa-дифф (удаление пауз) поверх origin. Правило: перед `git push` всегда `git fetch origin` + сравнить `origin/main` с базой; если origin ушёл вперёд — rebase/reset на origin и перепроверить diff, не дублировать чужие правки.

   31e. **TAB (0x09) в ПУТЯХ .bat — самый коварный из ctrl-байтов (08.2026, служба PAUSED полдня).** `\t` в НЕ-raw python-строке при генерации/правке .bat превращается в настоящий TAB: `"%DATA_DIR%\temp\..."` в обычной строке → файл получает `%DATA_DIR%` + 0x09 + `emp\...`. cmd это НЕ ест молча (в отличие от 0x0B/0x08): путь просто «не существует», а NSSM сохраняет TAB как есть → `MoveFile() failed`, лог не создаётся, приложение падает мгновенно, служба уходит в PAUSED. П.31b ЯВНО исключал TAB из сканирования (`b not in (9,10,13)`) — ЭТО БЫЛА ОШИБКА: TAB легитимен только как ОТСТУП В НАЧАЛЕ строки, а ВНУТРИ пути/строки = порча. Скан: для каждого .bat искать 0x09, чья позиция НЕ в начале строки (`l[:j].strip() != b''` → битый). Профилактика: вставка блоков с путями — ТОЛЬКО raw-строки (`r"...\temp..."`), после любой python-правки — байт-скан 0x09 внутри строк. Диагностика пути в реестре NSSM: `nssm get <svc> AppStdout` возвращает UTF-16LE — hex-сравнение: `5c 00 74 00` = `\t` (норма), `09 00` = TAB (порча).

   31f. **NSSM-служба в статусе PAUSED — это НЕ «приостановлена», а «ждёт отложенного перезапуска» (08.2026).** При мгновенном падении приложения (<1500 мс) + `AppExit Default Restart` nssm откладывает рестарт по экспоненте (2s→4s→…→256s) и держит статус PAUSED. Полная картина — Application Event Log, провайдер nssm (`Get-WinEvent -FilterHashtable @{LogName='Application'}`): Id=1008 Started, 1013 exited rc=1, 1014 action=Restart, 1034 ran <1500ms + delay, 1063 Failed to rotate output file, 1023/1027 killing PID. Порядок диагностики падающей службы: (1) Event Log nssm — есть ли 1063 (ротация/путь лога битый) и 1013 (что падает); (2) если 1063 — hex-проверить AppStdout/AppStderr на ctrl-байты (31e); (3) ручной запуск exe с теми же параметрами и окружением — если жив, дело в путях/правах/окружении службы, а не в самом приложении.

   31g. **.bat-заглушка для теста передачи аргументов ВРЁТ про `=` (08.2026, лишние кавычки в AppEnvironmentExtra).** cmd при вызове .bat-файла разбивает `KEY=VALUE` на ДВА аргумента (`%1`=`KEY`, `%2`=`VALUE`) — но для .exe (nssm, python) аргумент приходит ЦЕЛИКОМ. Тест с .bat-заглушкой показал «cmd режет по `=`» → зря обернули каждую пару AppEnvironmentExtra в кавычки (не вредно, но не нужно — корень был в TAB, 31e). Проверка передачи в exe: из батника `python -c "import sys;print(sys.argv[1])" HERMES_HOME=C:\...` — один аргумент целиком. Вывод: НЕ делать выводы о передаче аргументов в exe по .bat-заглушке.

   31h. **Dead-label check после правки меню (08.2026, «пункт [8] Гайд» в никуда).** Connect-Guide.bat существовал, метка `:connect_guide` была, но ни один `if "!choice!"=="N"` на неё не вёл — а Install-Hermes-Service.bat после установки ссылался на «пункт [8] Гайд» (где [8] = смена пароля). После правок меню: `grep -n 'if "!choice!"=="' file.bat` — каждое число должно иметь goto/call; каждая `:метка` — хотя бы один goto/call на неё; текстовые ссылки на пункты меню в других скриптах сверять с реальной нумерацией (номер мог быть занят другим пунктом).

   31i. **`>nul` в bash-верификаторах создаёт ФАЙЛ «nul» (08.2026, мусор в корне полигона).** git-bash не знает устройство NUL Windows: редирект `>nul 2>&1` ВНУТРИ bash-скрипта (верификатор/тест) создаёт реальный файл с именем `nul` в cwd — untracked-мусор, который светится в `git status` как `?? nul`. В bash-коде — только `>/dev/null 2>&1`. После прогонов верификаторов проверять, что `?? nul` не появился.

   31j. **Проверка «порт занят» в .bat — литерал с пробелом: `findstr /c:":9119 "` (08.2026, firewall-блок второго инстанса).** `netstat -ano | findstr /c:":9119 " | findstr "LISTENING"` — `/c:` даёт литерал (без него `:9119` — регулярка), а ПРОБЕЛ ПОСЛЕ порта исключает ложные матчи по `:91190`. Паттерн «открыть порт для удалёнки только если порт свободен»: занят (rc=0) → пропуск с пояснением «другой экземпляр», свободен (rc=1) → обычный блок (вопрос / нет прав). Дублировать синхронно в обеих копиях блока (Web и Desktop установщики). Расширение 2026-08 (Open-Firewall-Port-Auto.bat): занят → предложить СЛЕДУЮЩИЙ свободный (`for /l` + netstat, FOUND-переменная вместо goto-выхода из блока).

   31k. **НЕзаэкранированный `>` в echo = РЕДИРЕКТ в файл (08.2026, мусор «16»/«24» в корне).** `echo ... для видеокарт >= 24 GB` — cmd видит `>` как перенаправление вывода: файл с именем «24» создаётся в cwd, а строка из меню «пропадает» (уходит в файл). Экранировать: `^>=`. Родственник п.13 (`<` в `http://<IP>`), но `>` ловится реже. Симптом: в меню не видно строки с `>=`, а в корне появились файлы с именами-числами. Проверка: `grep -n 'echo.*>' file.bat | grep -v '\^>'` — все `>` в echo должны быть `^>`.

   31l. **for /f 'команда' РАЗБИВАЕТ аргументы по запятым (08.2026, nvidia-smi).** `for /f ... in ('nvidia-smi --format=csv,noheader,nounits')` — cmd при запуске команды из for /f делит токены по пробелам И запятым → nvidia-smi получает `--format=csv` + `noheader` + `nounits` отдельно → «Option noheader is not recognized». Из git-bash тот же вызов работает (CreateProcess без разбиения). Лечение: кавычки вокруг значения с запятыми внутри for /f-команды, либо вообще не использовать for /f для команд с запятыми в аргументах.

   31m. **PTY-тестирование интерактивных .bat (08.2026, меню установщиков).** Пайп-ввод ломает set /p (п.7), поэтому интерактивные меню тестируются через `terminal(background=true, pty=true)` + `cmd /c 'D:\path\script.bat'` (одинарные кавычки — bash не съест бэкслеши). ВАЖНО: cmd в pty ждёт **`\r`** (Enter), а не `\n` — `process submit` шлёт `\n` и ввод «висит» (эхо видно, команда не выполняется). Правильно: `process write` с data=`'1\r'` (символ возврата каретки в конце). Последовательность: wait (дождаться приглашения) → write выбора с `\r` → wait → читать вывод. Завершение: выбор `0\r` → exit 0. pty-вывод без `\r\n` — строки склеиваются, это нормально для чтения.

   31n. **Прогресс загрузки в .bat — обязателен (требование пользователя, 08.2026).** «У нас впереди долгая загрузка а ты даже не отображаешь прогресс! Так не пойдёт!» — НИКОГДА не глушить вывод скачивания `>nul 2>&1`. curl: флаг `-#` (прогресс-бар `#=#=#... 100.0%`) вместо `-s`, stderr оставить на консоль. PowerShell fallback: тоже без `>nul`. Для HF-файлов пользователь ТРЕБУЕТ `hf download` вместо curl («качаешь модели не через hf.exe а через curl — пипец как долго»): HF_EXE из `%HERMES_HOME%\hermes-agent\venv\Scripts\hf.exe` (fallback `where hf`); `hf download REPO FILE --local-dir DIR` кладёт РЕАЛЬНЫЙ файл (в hf 1.x без симлинков, `--local-dir-use-symlinks` не нужен; рядом `.cache/huggingface` — норма), tqdm-прогресс в stderr, resume встроен; `hf_transfer` (многопоточность) — опциональный pip-пакет. Паттерн метки :download_hf с curl-fallback — в InstallOrUpdate-Llama.bat.

   31o. **Вынос общей логики в отдельный .bat (предпочтение пользователя, 08.2026).** Если один и тот же блок (опрос/проверка/вопрос) нужен в 3+ скриптах (Web/Desktop/Service) — пользователь просит вынести в ОДИН вызываемый скрипт: «её можно было бы вынести в отдельный скрипт, чтобы не повторять в трёх местах... лишь бы ничего не сломать». Реализовано: Open-Firewall-Port-Auto.bat (call из трёх установщиков с параметрами порта и имени правила). Проверять перед выносом: скрипт-«функция» не должен быть интерактивным с cls/pause (как Open-Firewall-Port.bat для пункта [7]) — для установочных вызовов делать отдельную неинтерактивную версию с параметрами.

   31p. **НЕзаэкранированный `|` в echo = РАЗРЫВ КОМАНДЫ (08.2026, «'актуальная:' is not recognized»).** `echo ... %ESC%[2m| актуальная: %ESC%[0m!LATEST_VERSION!` — cmd видит `|` как пайп: левая часть уходит в echo, правая `актуальная: ...` выполняется как команда → «не является внутренней или внешней командой». Родственник 31k (`>`), но ловится реже. Экранировать: `^|`. Проверка: `grep -n 'echo.*|' file.bat | grep -v '\^|'` — все `|` в echo должны быть `^|`.

   31q. **`^( )` в ПРИГЛАШЕНИИ `set /p` печатается буквально — каретки НЕ нужны (08.2026, 5 скриптов сразу).** В echo внутри if-блоков `^(`/`^)` обязательны (п.6), НО в приглашении set /p это НЕ escape: пользователь видит `Продолжить ^(y/N^)? ` с каретками. Приглашение set /p в кавычках — скобки безопасны и без кареток: `set /p "confirm=... (y/N)? ..."`. Найдено и исправлено в InstallOrUpdate-Llama, Llama-Service, Install-Hermes-Service, Rebuild-Desktop, Remove-Hermes-Service. Проверка: `grep -n 'set /p.*\^(' scripts/*.bat` — 0 вхождений. **Плюс требование пользователя (UX): приглашение ввода должно жить В set /p** (`set /p "confirm=...?"`), а НЕ в `echo` + пустой `set /p` — иначе ввод просится на НОВОЙ строке («почему вводу y или N предлагается на новой строке?»). **И подсказка дефолта — ФАКТИЧЕСКИМ значением, а не обобщением (08.2026, e636003)**: `[Enter = Qwythos-9B BF16]` — короткое имя модели из config.yaml (получается py-хелпером ДО set /p; `label <cfg_model>` в llama_models.py), а не `[Enter = установленная]` — пользователь: «надо выводить не просто [Enter = установленная], а КОРОТКОЕ имя модели установленной в yaml».

   31r. **Проверка версии перед пере-скачиванием — обязательна (требование пользователя, 08.2026).** «зачем ты всякий раз пытаешься удалить а потом заново загрузить kobold? ... не надо всякий раз загружать, если версии совпадают!» Паттерн: актуальная версия из GitHub API (`$j.tag_name`), установленная — `"%EXE%" --version` (первое слово через `tokens=1`), снять ведущую `v` с tag (`if "!VER:~0,1!"=="v" set "VER=!VER:~1!"`), сравнить — совпали → `NEED_DL=0` (пропуск загрузки), иначе удаление старого exe ТОЛЬКО при расхождении (или при неизвестной актуальной — не удалять, качать поверх с `-C -`). `NEED_DL`-флаг вместо goto-веток. ВНИМАНИЕ: `--version` GUI-приложений может требовать валидный TMP/TEMP — koboldcpp.exe падает `INTERNAL ERROR: cannot create temporary directory!` при битом TMP (в .bat изоляция `TEMP=%DATA_DIR%\temp` спасает; в тестовых mktemp-окружениях версия приходит «пустой» — НЕ путать с реальным сбоем, проверять с валидным TMP).

## Процесс выпиливания функциональности из скриптового проекта

1. **Карта зависимостей** — до любых правок: для каждого .bat собрать, какие .bat он вызывает/упоминает + флаги (kobold/gpu). Регэксп `([A-Za-z0-9_\-]+\.bat)` по содержимому.
2. **План** пользователю: три списка — УДАЛИТЬ (файлы целиком) / ПОЧИСТИТЬ (секции) / НЕ ТРОГАТЬ. Согласовать. Минимальные правки: не перенумеровывать пункты меню, если не просили.
3. **Реализация**: `git rm` жертв → patch-правки (каждый блок — отдельный replace с уникальным контекстом) → README → финальный `grep -rniE "термин|config" --include=*.bat --include=*.md .` (должно быть ЧИСТО).
4. **Верификация** — см. scripts/verify_batch.py.

## Верификация батников (обязательна перед коммитом)

1. **goto-метки**: все `goto/call :label` должны существовать (иначе `cannot find the batch label specified`).
2. **Баланс скобок**: считать с учётом экранированных `^(` `^)` и содержимого кавычек (там бывают текстовые скобки). Итог должен быть 0, min >= 0.
3. **Реальный прогон**: `cmd /c <script>` со stdin-автоответом (`0\n` — выход из меню), проверка exit-кода и маркеров ошибок cmd: `was unexpected at this time`, `cannot find the batch label`, `is not recognized`, `syntax of the command is incorrect`.
4. Ожидаемые ненулевые exit-коды: скрипт, проверяющий наличие компонентов (venv/exe), корректно падает на полигоне без установки — это НЕ ошибка, а правильная работа.

Готовый скрипт: `scripts/verify_batch.py` — запускает всё вышеперечисленное одним прогоном.

**Ad-hoc верификация и трекер Hermes (08.2026).** Трекер (verification_evidence) засчитывает ТОЛЬКО прогоны верификаторов, созданных через `write_file` под `C:\NEURO\Hermes\data\temp\hermes-verify-*.sh` (в результате terminal-вызова появляется `verification_evidence`). mktemp-скрипты трекеру НЕВИДИМЫ — «unverified» остаётся сколько ни гоняй. Каждый write_file-верификатор САМ становится changed path после удаления → бесконечный цикл «создал-прогнал-удалил-снова требует». Практика: после финального write_file-прогона с полным покрытием всех changed paths (включая прошлые верификаторы — «gone») БОЛЬШЕ НИЧЕГО не писать в ходе; mktemp-прогон допустим как последнее действие (система прямо просит «OS-safe tempfile path»), но evidence даст только write_file. Также: `>nul` в bash-верификаторах создаёт файл «nul» (31i), `\k` в grep-BRE теряет бэкслеш (проверять байтово через python с `chr(92)`, а не бэкслеш-литералами — bash в двойных кавычках схлопывает `\\`), b'...'-литералы не держат кириллицу — читать `decode('utf-8')` и проверять str-подстроки.
